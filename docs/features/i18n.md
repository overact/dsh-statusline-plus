# UI languages

The plugin's interface follows the Host's locale service. It registers its `zh` and `en`
dictionaries under the `statusline` namespace and asks the service for text, so the Host's
language selector and fallback chain apply. DSH does not translate the plugin's strings; the
plugin supplies every translation.

## Code

`STR`, `LOCALE_NS`, `translate`, `activeLocale`, `currentLang`, `t`, `useLocaleRevision` in
`lib/client.js`; the registration in `apply`.

## Behavior

- **Host locale service.** `apply` registers `STR` with `ctx.get('locale')` and binds `t` to
  the `statusline` namespace. The service resolves the active language, then falls back to
  English for a missing key; the plugin never invents a translation.
- **Older Hosts.** Without the service, `t` reads `STR` directly and falls back to English.
- **Live switch.** `useLocaleRevision` subscribes to the service and re-renders the slot
  roots (composer dock, header chip, sidebar dot, settings) when the language changes.
- **Adding a language.** Add the dictionary to `STR`; no `currentLang` change is needed. Keep
  its key set equal to English so the fallback only covers keys added later.
- **Dates and account metadata.** `activeLocale` feeds `toLocaleString` and the account
  client metadata, so a `ja` Host sends `ja` rather than `en-US`.

## Tests
